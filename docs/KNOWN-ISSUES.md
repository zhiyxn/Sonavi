## Critical（2）

### P13-CR-001：FLAC 原始流 seek 后长时间缓冲且切歌无法恢复

- 状态：`CLOSED`（2026-09-18 Windows 真机 `PLAY-02` 复验通过）。
- 平台：Windows 11 x64；当前源码预览；真实 Navidrome 服务器；`audio/flac` 原始音频。
- 复现：播放 FLAC 原始流，拖动或多次点击进度条，随后尝试切换歌曲。
- 实际：进度跳转后进入长时间缓冲，切歌也未恢复播放。
- 预期：seek 取消旧 Range 请求后及时释放上游连接；新 Range 或新歌曲请求可独立开始。
- 脱敏证据：导出时间 13:05:09；12:52:53 的 `audio-original` / `audio/flac` 请求以 HTTP 206 结束为 `cancelled`；12:53:42 起记录 130456 ms 缓冲；12:55:56 的 `buffer-start` 到导出时仍无对应 `buffer-end`，已持续至少 553099 ms。日志不含歌曲 ID、URL 或凭据。
- 根因：（1）进度 Slider 是受控值，但拖动期间的 `update:modelValue` 没有保存，每次移动都被旧播放时间覆盖；（2）`sonavi-media` 下游取消没有主动中止上游 fetch，旧 FLAC Range 下载可继续占用连接；（3）“上一首”在当前进度超过 3 秒时被隐式改为重播当前曲目，seek 后必然触发错误语义。
- 最小修复：Slider 在拖动时保留临时位置，松手后才提交一次 seek；下游取消时主动 `abortController.abort()`；“上一首”始终按名称切换前一队列项，只在没有前一项时从头播放当前曲目。
- 回归测试：Slider 修复前拖动到 4.2 秒仍回退为 0；seek 后点击上一首的测试在修复前仍为 `two`，修复后正确切到 `one`。播放器 19/19、媒体协议 17/17 通过。Node.js 22.21.1 下 lint、typecheck、29 文件/159 项全量测试及生产构建通过；新构建的 Windows 源码预览已启动。
- 影响范围：共享 main 媒体代理，Windows 与 macOS 同时受益；macOS Intel/arm64 尚未真机复验。
- 对应用例：`PLAY-02` / `C-03`。

### P13-CR-003：保存播放设置会清空或使当前队列媒体失效

- 状态：`CLOSED`（2026-09-18 Windows 真机确认补充修复后保存设置、持续播放与队列行为正常）。
- 平台：Windows 11 x64；当前源码预览；真实服务器。
- 复现：队列中存在当前歌曲时进入设置，仅修改播放模式或直接点击“保存播放与网络设置”。
- 实际：第一层问题会清空当前歌曲和整个队列；修复后界面状态保留，但 main 仍撤销正在播放的音频请求和队列媒体句柄，随后出现长时间缓冲且无法可靠继续 seek/切歌。
- 预期：普通播放策略保存不应销毁当前播放状态；只有代理真正切换、旧连接必须重置时才安全停止播放并清理旧查询上下文。
- 根因：（1）设置页丢弃 `connectionsReset` 并无条件通知应用外壳停止播放器；（2）第一层修复后，main 的设置 IPC 仍无条件取消搜索、撤销媒体请求及全部媒体句柄，即使 `connectionsReset=false`。队列因此保留了已失效的不透明媒体 URL。
- 脱敏证据：16:42:24.289 一个 FLAC 音频请求与两个封面请求在同一毫秒被取消；433 ms 后进入缓冲，随后出现 20762 ms 与 18320 ms 的连续缓冲。同期 API 和 scrobble 均为 HTTP 200，没有 timeout、鉴权或 broken-stream 错误。
- 最小修复：renderer 与 main 均以 `connectionsReset` 为门控；只有代理实际切换时才停止播放器、清查询、取消搜索并撤销媒体请求/句柄。后续 P12R-MA-003 按新验收要求扩展为：播放策略确实变化时保持队列，并安全刷新其播放句柄；能保留进度则切换当前流，否则从下一曲生效，仍不会清空队列或撤销整个会话。
- 回归测试：renderer 测试确认普通保存不调用 `player.stop()`；main 会话撤销测试在修复前对 `connectionsReset=false` 返回 `true`，修复后不执行任何撤销，而 `true` 分支仍各执行一次。相关 3 文件/31 项、lint、typecheck、29 文件/162 项全量测试及生产构建通过。
- 影响范围：共享 renderer 与 main 设置链路；Windows 已复验，macOS Intel/arm64 未验证。
- 对应用例：`PLAY-03`。

原 RC-C-001 已修复：媒体句柄改为每次会话密钥加密、带会话 epoch 的无状态不透明 token，不再由 2,000 项全局 FIFO 淘汰。单元测试确认先创建队列音频、再创建 10,000 个封面句柄后音频仍可解析；断开、忘记账号和退出仍会整体失效旧句柄。

## 诊断与网络策略待决（2026-09-16）

- API 超时仍是固定 12 秒：`getArtists` 已放宽响应上限到 16 MiB，但超时没有同步放宽；真实服务器上仍出现 12 秒无响应记录，需要直连与代理对照后再决定是否按端点区分超时。
- renderer 用 TanStack Vue Query 默认 `retry: 3`，单个查询失败最多产生 4 次超时尝试；诊断条目没有尝试序号，无法区分“一个查询重试多次”与“多次用户操作”，要分组必须从 renderer 传递请求标识。
- 2026-09-18 真实诊断新证据：28 个 `getCoverArt` 在约 10 ms 内同时发出，耗时 0.96–31.28 秒；随后 `getAlbumList2` 出现两组完整的“12 秒超时 + 1/2/4 秒退避”四次尝试，与默认重试完全吻合。日志支持“封面并发过高与专辑排序查询过慢共同导致”，但不足以单独证明代理或服务器哪一侧是唯一根因。
